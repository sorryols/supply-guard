# LibSentinel — засіб аналізу безпеки бібліотек з відкритим кодом

LibSentinel перевіряє **оновлення бібліотек Python (PyPI)** перед тим, як вони потраплять у ваш проєкт.
Засіб аналізує перехід від версії, що вже використовується (v0), до нової версії (v1), і приймає рішення:
**допустити**, **допустити з попередженням** або **заблокувати**. Рішення передається в CI/CD через код завершення.

Засіб реалізує метод, описаний у розділі 2 магістерської кваліфікаційної роботи
«Метод та засіб аналізу безпеки бібліотек з відкритим кодом».

## 1. Можливості

| Група | Що перевіряється | Індикатори |
|---|---|---|
| Автори й метадані (`avt_meta.py`) | Видавець і атестації PEP 740, нові власники в PyPI, періодичність релізів, тег версії в репозиторії, **довіра до авторів змін** (супровідник → 1, постійний учасник → 0,6, новий учасник → 0,2 і попередження, невідомий → 0) | A1–A5 |
| Статичний аналіз (`sast.py`) | Різниця між версіями, код встановлення (`setup.py`, `pyproject.toml`), нові небезпечні виклики, мережа під час імпорту, доступ до токенів і ключів, закодовані рядки, файли, яких немає в репозиторії | S1–S6, К1–К3 |
| Залежності (`deps.py`) | Нові залежності, тайпосквотинг (відстань Левенштейна), нові й малоактивні пакети, вразливості **OSV**, база **OpenSSF Malicious Packages** | D1–D4, К4 |
| Динамічний аналіз (`dast.py`) | Встановлення та імпорт у контейнері Docker без мережі під `strace`, файли-приманки з фіктивними обліковими даними | B1–B3, К5 |

Додатково: режим перевірки всього `requirements.txt` (порівняння з git-гілкою), звіти у консоль, JSON і SARIF
(вкладка **Security** на GitHub), кеш результатів у SQLite, блокові тести та експериментальний стенд.

## 2. Архітектура

```
libsentinel/
├── main.py         # інтерфейс командного рядка
├── analyzer.py     # алгоритм аналізу (рис. 2.2): етапи 1–6, дострокова зупинка, умовний DAST
├── fetch.py        # етап 1: завантаження з PyPI, перевірка SHA-256, безпечне розпакування
├── avt_meta.py     # етап 2: автори й метадані (A1–A5, τ — формула 2.3)
├── sast.py         # етап 3: різниця версій і статичний аналіз AST (S1–S6, К1–К3)
├── deps.py         # етап 4: залежності, OSV, OpenSSF (D1–D4, К4)
├── dast.py         # етап 5: динамічний аналіз у Docker (B1–B3, К5)
├── scoring.py      # формула 2.4 («шумне АБО»), пороги, правило рішення
├── report.py       # звіт: консоль, JSON, SARIF
├── reqdiff.py      # порівняння requirements.txt (файл або git)
├── cache.py        # кеш SQLite
├── net.py          # клієнти PyPI, GitHub, OSV
├── models.py       # структури даних (індикатор, контекст, звіт)
├── config.py       # завантаження конфігурації
├── data/default_config.yaml   # ваги, пороги, рівні довіри (табл. 2.1)
├── data/top_pypi.txt          # популярні бібліотеки для перевірки тайпосквотингу
└── sandbox/        # Dockerfile і runner.py пісочниці
```

Послідовність роботи: **отримання даних → автори й метадані → статичний аналіз → залежності →
попередня оцінка Pa → (динамічний аналіз, якщо Pa ≥ θd або змінено код встановлення) → остаточна оцінка і рішення**.
Якщо спрацював критичний індикатор (К1–К5), аналіз зупиняється одразу з рішенням «заблокувати».

## 3. Вимоги

- Ubuntu 22.04 або 24.04 (також працює на Kali Linux, ParrotOS; на Windows — без динамічного аналізу або з Docker Desktop);
- Python 3.9+ (рекомендовано 3.10–3.12);
- Docker (для динамічного аналізу);
- git;
- доступ до інтернету (pypi.org, api.github.com, api.osv.dev, github.com);
- ~2 ГБ вільного місця (образ пісочниці та кеш).

## 4. Встановлення на Ubuntu

### Варіант А — автоматично

```bash
# 1. Отримати код (з GitHub або розпакувати архів)
git clone https://github.com/OWNER/libsentinel.git      # або: unzip libsentinel.zip
cd libsentinel

# 2. Запустити скрипт встановлення
bash install.sh
```

Скрипт встановить системні пакети, Docker, створить віртуальне середовище `.venv`, додасть команду
`libsentinel` у `~/.local/bin`, збере образ пісочниці та завантажить бази даних.

> Якщо скрипт повідомив, що вас додано до групи `docker`, **вийдіть із системи й увійдіть знову**
> (або виконайте `newgrp docker`) і запустіть `bash install.sh` ще раз.

### Варіант Б — вручну

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip git docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER        # потім перелогінитись

cd libsentinel
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

libsentinel sandbox-build            # зібрати образ пісочниці (2–5 хв, один раз)
libsentinel update-data              # завантажити базу OpenSSF і список популярних бібліотек
libsentinel doctor                   # перевірити середовище
```

Очікуваний результат `libsentinel doctor`:

## 5. Налаштування

### 5.1 Токен GitHub (рекомендовано)

Без токена GitHub дозволяє лише 60 запитів на годину, і оцінка авторів змін буде менш точною
(обсяг змін рахується в комітах, а не в рядках, ролі — за історією внесків).

1. GitHub → **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**.
2. Repository access: **Public repositories (read-only)**. Додаткові дозволи не потрібні.
3. Додайте токен у `~/.bashrc`:

```bash
echo 'export GITHUB_TOKEN="github_pat_..."' >> ~/.bashrc
source ~/.bashrc
```

У GitHub Actions токен передається автоматично (`${{ github.token }}`).

### 5.2 Конфігурація (ваги, пороги, рівні довіри)

Значення за замовчуванням — у `libsentinel/data/default_config.yaml` (відповідають таблиці 2.1 роботи).
Щоб змінити їх, створіть власний файл лише з потрібними параметрами:

```yaml
# my-config.yaml
thresholds:
  warn: 0.3     # θ1
  block: 0.6    # θ2 (наприклад, значення після калібрування)
  dynamic: 0.3  # θd
weights:
  D2: 0.6
trust:
  contributor: 0.5
dast:
  runtime: runsc   # gVisor замість стандартного runc (див. розділ 10)
```

і запускайте з `--config my-config.yaml`.

### 5.3 Кеш

Кеш зберігається в `~/.cache/libsentinel/` (архіви пакетів, відповіді API, результати, база OpenSSF).
Змінити розташування: `export LIBSENTINEL_CACHE=/шлях`. Очистити: `libsentinel cache-clear`.

## 6. Запуск

### 6.1 Аналіз оновлення однієї бібліотеки

```bash
libsentinel analyze requests --from 2.31.0 --to 2.32.3
```

### 6.2 Нова залежність (поточної версії немає)

```bash
libsentinel analyze tqdm==4.66.5
```

### 6.3 Перевірка змін у requirements.txt

```bash
# порівняння з іншим файлом
libsentinel requirements --old requirements.old.txt --file requirements.txt

# порівняння з гілкою git (так працює CI)
libsentinel requirements --git-base origin/main --file requirements.txt
```

Аналізуються лише залежності із закріпленою версією (`==`). Для інших виводиться примітка.

### 6.4 Локальні архіви (без завантаження з PyPI)

```bash
libsentinel analyze mylib --from 1.0.0 --to 1.1.0 \
    --old-archive dist/mylib-1.0.0.tar.gz --new-archive dist/mylib-1.1.0.tar.gz --offline
```

### 6.5 Основні параметри

| Параметр | Призначення |
|---|---|
| `--dast auto\|always\|never` | динамічний аналіз за умовою методу (типово), завжди або ніколи |
| `--json FILE` | повний звіт у JSON |
| `--sarif FILE` | звіт у SARIF для GitHub Code Scanning |
| `--config FILE` | власна конфігурація |
| `--offline` | без звернень до PyPI/GitHub/OSV |
| `--no-cache` | повторний аналіз без кешу |
| `-v` / `-q` | усі докази / лише підсумок |
| `--fail-on block\|warn` | (requirements) коли повертати ненульовий код |

### 6.6 Коди завершення

| Код | Рішення | Поведінка в CI/CD |
|---|---|---|
| 0 | допустити | збирання продовжується |
| 1 | допустити з попередженням | продовжується (або зупиняється з `--fail-on warn`) |
| 2 | заблокувати | збирання зупиняється |
| 3 | помилка аналізу | збирання зупиняється |

## 7. Як читати звіт

```
══════════════════════════════════════════════════════════════════════
 LibSentinel 1.0.0 · аналіз оновлення бібліотеки
 libsentinel-demo  1.0.0 → 1.1.3
══════════════════════════════════════════════════════════════════════
 Рішення:                 ЗАБЛОКУВАТИ (код завершення 2)
 Ймовірність аномалії Pa: 1.00
 Довіра до оновлення D:   0.00
 Довіра до авторів τ:     —
 Рівень небезпеки:        критичний
 Динамічний аналіз:       виконано

 Індикатори, що спрацювали (3)
  K5 [КРИТИЧНИЙ] Читання файлів-приманок — блокування
      • Прочитано файл-приманку /home/sandbox/.ssh/id_rsa (фаза: встановлення)
  S1 Зміна коду, що виконується під час встановлення — внесок 0.40 (x=1.00, p=0.4)
      • sdist/setup.py Змінено код, що виконується під час встановлення (8 змінених рядків)
  S2 Нові небезпечні виклики — внесок 0.40 (x=1.00, p=0.4)
      • sdist/setup.py:1 Нова можливість «dynexec»
        _o = __import__("".join(["o", "s"]))
```

- **Pa** — ймовірність аномалії за формулою (2.4); **D = 1 − Pa** — ступінь довіри до оновлення;
- **τ** — ступінь довіри до авторів змін за формулою (2.3);
- **внесок** індикатора — p·x; індикатори відсортовано за спаданням внеску, критичні — першими;
- під кожним індикатором — **докази**: файл і рядок коду, значення метаданих або запис журналу системних викликів;
- «Не оцінено» — індикатори, для яких забракло даних (наприклад, недоступний GitHub), з причиною.

## 8. Інтеграція з Git і GitHub Actions (CI/CD)

### 8.1 GitHub Actions (рекомендовано)

1. Розмістіть код засобу в окремому репозиторії GitHub (наприклад, `OWNER/libsentinel`) і створіть тег `v1`:
   ```bash
   git init && git add . && git commit -m "LibSentinel 1.0.0"
   git remote add origin https://github.com/OWNER/libsentinel.git
   git push -u origin main
   git tag v1 && git push origin v1
   ```
2. У **своєму проєкті** створіть файл `.github/workflows/libsentinel-check.yml` — скопіюйте
   [`ci/libsentinel-check.yml`](ci/libsentinel-check.yml) і замініть `OWNER` на свій логін.
3. Створіть pull request, що змінює `requirements.txt`. Робочий процес:
   - встановить засіб і збере пісочницю;
   - порівняє `requirements.txt` з цільовою гілкою;
   - проаналізує кожну змінену бібліотеку;
   - покаже таблицю на сторінці запуску (Summary), збереже звіт як артефакт `libsentinel-report`;
   - завантажить знахідки у **Security → Code scanning** (формат SARIF);
   - **завершиться помилкою, якщо оновлення заблоковано** (код 2).
4. Щоб заборонити злиття небезпечних оновлень: **Settings → Branches → Add branch protection rule →
   Require status checks to pass → LibSentinel / dependency-security**.

Параметри дії (`with:`): `requirements-file`, `fail-on` (`block`/`warn`), `dast` (`auto`/`always`/`never`),
`config`, `base-ref`, `upload-sarif`.

> Для приватних репозиторіїв вкладка Code scanning потребує GitHub Advanced Security;
> якщо її немає, крок завантаження SARIF буде пропущено без помилки, решта працює.

### 8.2 Інші CI/CD (GitLab CI, Jenkins тощо)

Засіб — звичайна консольна програма, тому достатньо викликати її в конвеєрі:

```yaml
# .gitlab-ci.yml (раннер без Docker — динамічний аналіз вимкнено)
dependency-security:
  image: python:3.12
  script:
    - pip install git+https://github.com/OWNER/libsentinel.git
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    - libsentinel requirements --git-base origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME
        --file requirements.txt --dast never --json report.json
  artifacts:
    paths: [report.json]
```

Ненульовий код завершення зупиняє конвеєр. Якщо раннер має доступ до Docker (shell-раннер або
Docker-in-Docker), додайте крок `libsentinel sandbox-build` і приберіть `--dast never`.

### 8.3 Локальний git-хук (перевірка перед комітом)

```bash
cd ваш-проєкт
cp /шлях/до/libsentinel/hooks/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Тепер `git commit` зі зміненим `requirements*.txt` запускає перевірку і зупиняє коміт при рішенні
«заблокувати». Пропустити одноразово: `git commit --no-verify`. Вимкнути DAST у хуку:
`export LIBSENTINEL_DAST=never`.

## 9. Тестування та експерименти

### 9.1 Блокові тести

```bash
source .venv/bin/activate
pytest -v                      # усі тести (77); тести з Docker пропускаються, якщо пісочниці немає
pytest -v -k "not dynamic"     # лише тести без Docker
```

Тести покривають кожен модуль: формули (2.3) і (2.4), правило рішення, виявлення кожного індикатора,
розбір журналів strace, безпечне розпакування архівів, порівняння requirements, формати звітів.

### 9.2 Експериментальна перевірка

```bash
# 1. Синтетичні зразки: 5 безпечних оновлень і 8 безпечних імітацій атак
python experiments/make_synthetic.py

# 2. Прогін на 30 реальних легітимних оновленнях популярних бібліотек + синтетичних зразках
python experiments/run_experiment.py experiments/benign_real.csv experiments/synthetic/synthetic.csv --sweep
```

Скрипт виводить таблицю результатів і показники: **TP, FP, FN, TN, точність, повнота, F1, частка хибних
спрацювань (FPR), середній час аналізу, частка оновлень із динамічним аналізом**. Параметр `--sweep` підбирає
поріг блокування θ2 за максимумом F1. Результати зберігаються в `experiments/results/` (CSV і JSON).
Приклад результатів — у `experiments/results_example/`.

Формат власного набору даних (CSV):

```csv
name,old,new,label,kind,old_archive,new_archive
requests,2.31.0,2.32.3,0,benign-real,,
mylib,1.0.0,1.0.1,1,malicious,/path/mylib-1.0.0.tar.gz,/path/mylib-1.0.1.tar.gz
```

`label`: 0 — безпечне оновлення, 1 — шкідливе. Колонки архівів заповнюються лише для локальних файлів.

### 9.3 Реальні шкідливі зразки

Для перевірки на справжніх шкідливих пакетах можна використати відкритий набір даних
[DataDog malicious-software-packages-dataset](https://github.com/DataDog/malicious-software-packages-dataset)
(архіви зашифровано паролем `infected`). **Працюйте з ним лише у віртуальній машині**, ніколи не встановлюйте
ці пакети вручну, і використовуйте засіб лише в режимі аналізу.

## 10. Безпека та обмеження

- Статичний аналіз **не виконує** код пакета — лише розбирає його модулем `ast`.
- Архіви розпаковуються з перевіркою шляхів, посилань і розміру (захист від path traversal і «zip-бомб»).
- Динамічний аналіз запускає код пакета **лише в контейнері**: `--network none`, `--cap-drop ALL`,
  `no-new-privileges`, файлова система лише для читання, обмеження пам'яті, процесів і часу,
  непривілейований користувач. Для сильнішої ізоляції встановіть gVisor за офіційною інструкцією
  (https://gvisor.dev/docs/user_guide/install/), зареєструйте його в Docker (`sudo runsc install &&
  sudo systemctl restart docker`) і вкажіть у конфігурації `dast.runtime: runsc`.
- Контейнер не дає абсолютної ізоляції. Для експериментів із реальним шкідливим кодом використовуйте окрему ВМ.
- Обмеження: аналізуються бібліотеки PyPI; код на C/Rust у бінарних wheel не аналізується статично;
  шкідлива поведінка, що проявляється лише за певних умов (дата, середовище), може не проявитися в пісочниці;
  оцінка авторів можлива лише для репозиторіїв на GitHub; A2 оцінюється, починаючи з другого запуску
  (порівнюються збережені знімки складу власників).

## 11. Усунення несправностей

| Проблема | Рішення |
|---|---|
| `permission denied ... docker.sock` | `sudo usermod -aG docker $USER`, перелогінитись |
| `Docker-демон недоступний` | `sudo systemctl start docker` |
| `GitHub API — HTTP 403` | закінчився ліміт запитів — задайте `GITHUB_TOKEN` |
| A3/A5 «не оцінено» | у метаданих немає посилання на GitHub або репозиторій недоступний |
| Встановлення в пісочниці завершилося з помилкою | пакет потребує бекенда збирання, якого немає в образі — додайте його в `libsentinel/sandbox/Dockerfile` і виконайте `libsentinel sandbox-build` |
| Застарілий результат | `--no-cache` або `libsentinel cache-clear` |
| `libsentinel: command not found` | `source .venv/bin/activate` або додайте `~/.local/bin` у PATH |
